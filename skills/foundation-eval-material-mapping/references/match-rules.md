# 匹配规则库（指标 ↔ 存量文件）

`match_items.py` 用「规则层 + 词面层 + 门控」三层把文件指派给指标要点。本文件是口径说明与调参指南。

> **v2 内核（倒排索引 + 词长加权 + 特异性门控）** 是踩过坑改出来的。v1 的失败方式是**过配**：某要点命中 1154 个文件，`已归位` 数字好看但全是错的。改动点与原因见 §六。

## 一、三层打分

### 第 1 层：规则层（决定候选范围）

强规则表见 §二。命中规则只说明"这个概念出现在这个板块"，是**候选范围**，不是结论。

### 第 2 层：词面层（决定候选精度）

- **特征词只取自「三级指标名 + 考查要点」**。刻意**不取二级指标名**——二级名多为通名（如"财务资产管理"），混进来会让"会计人员配备"这类要点也被审计报告命中。
- 取词为 2–4 字 CJK n-gram，去停用词；
- **词长加权**：4 字 = 3 分 / 3 字 = 2 分 / 2 字 = 1 分（越长越具体，越能证明对口）；
- 通过**倒排索引**（词 → 文件 id 集合）反查，避免「要点数 × 文件数」的暴力比对（规模随指标版本与存量库而定，不预设固定值）。

**同义词扩展**（`SYNONYM`）：指标用词与文件命名用词常常不同——指标说"结项"，文件叫"总结"。只在这个尺度上做扩展：结项↔结题/总结/验收/决算/终期/成果；论证↔可行性/方案/计划书/立项/申请书；执行↔实施/进度/中期/拨付/采购/合同/协议；表彰↔荣誉/奖励/称号/先进；检查↔抽查/督查/巡查/核查 等。**不放宽到概念近义**（那等于把规则层的粗放又搬回来）。

### 第 3 层：门控（决定是否够格）

```
合格条件：词面分 >= 2
      或  词面分 >= 1 且 规则分 >= 3
```

这条门控是 v1 过配的根治手段：**光有规则命中、没有任何词面重合的文件，不允许被指派**。

### 得分与阈值

```
得分 = 规则分 + min(词面分, 12) + 载体修正 + 年度修正
载体修正：doc +0.5 / image 0 / video −0.5 / raw −1.0 / other −0.5
年度修正：年度在窗口内或未标注 +0.5
指派阈值：得分 >= 4 且 >= 最高候选的 85%（多指派）
```

## 三、状态四档（不可混用）

| 状态 | 判定 | 含义 | 机构动作 |
|---|---|---|---|
| **已归位** | 有 ≥1 个 `high` 文件 | 该文件的最优归属就是本要点，且词面分 ≥4、规则分 ≥3 | 抽查即可 |
| **待确认** | 只有 `medium` 文件 | 机器不确定是否对口 | **人工逐行判定** |
| **外部征询** | 要点文本含"登记管理机关评价/业务主管单位评价"等 | 材料由评估机构发函取得，机构侧本就没有可交材料 | 无需自备；日常合规留痕即可 |
| **缺项** | 无任何命中 | 存量中确实没有 | 按清单补料 |

**`high` 只给该文件的「最优归属要点」**：一个文件被多指派时，只有得分最高的那个要点算 high，其余一律 medium。多指派本身就是"这份文件究竟归哪一项"的判断问题，必须交人。

## 四、过宽要点（结构性难点，不是 bug）

**症状**：某要点候选数 > 60（脚本会打印告警与清单）。

**成因分两类**：

1. **规则过宽**——关键词太通用（补机构专有名词即可，见 §五）。
2. **结构性矩阵**（无法靠关键词解决）：**机构的项目材料按"项目"组织，而指标按"管理环节"组织**（论证/申报 → 运作 → 结项）。同一项目的文件夹里，申报书、执行协议、结项总结混在一起，**文件名不含管理环节语义**，任何关键词规则都无法自动切分。典型就是 `3.2 公益项目` 全系列。

**处置规则（脚本已内置）**：

| 项 | 规则 |
|---|---|
| 候选上限 | 超过 `OVERBROAD=60` 视为过宽 |
| 保留候选 | 仅留前 `OVERBROAD_CAP=15` 个作为"人工挑选建议" |
| 置信度 | **永不判 high**，一律 `待确认` |
| 归档就位 | **一律不实体化**（0 个文件）——放几个"看起来相关"的文件进归档树，只会制造"材料已齐"的假象 |
| 交付提示 | 在待确认清单的"类别标注"列写「规则过宽」，处置建议写明需人工从原始库挑选 |

**正确的应对不是继续加关键词**，而是把该板块转为人工挑选工单（矩阵型要点清单），并在给机构的说明里点明这一点。

## 五、机构专用规则（extra_rules.json）

**硬边界**：通用规则进专家包；**机构专属信息（项目名、业务专名、属地党建口径、合作方名）一律不进专家包**——它们属于客户信息，随任务放在**工作目录**里注入。脚本运行时自动加载 `<工作目录>/extra_rules.json`（也可用 `--extra-rules` 显式指定）。

文件格式（JSON 数组，字段：`label` 规则名 / `pattern` 正则 / `prefixes` 目标编号前缀 / `weight` 权重 2–4）：

```json
[
  {"label": "项目名称库", "pattern": "<项目一>|<项目二>|<项目三>", "prefixes": ["3.2"], "weight": 4},
  {"label": "属地党建专名", "pattern": "<联党委全名>|<党建品牌名>", "prefixes": ["2."], "weight": 4}
]
```

| 症状 | 补什么 | 写在哪 |
|---|---|---|
| 某板块文件全挤在少数要点且候选数百 | 补**项目名/专有名词**（权重 4） | `extra_rules.json` |
| 覆盖率虚高、待确认一片 | 补**部门/栏目名** | `extra_rules.json` |
| 党建板块缺失但盘上有材料 | 补**属地党建口径**（联党委/功能型党支部/党建指导员/主题党日） | 通用缺失时改脚本 `STRONG_RULES`，机构专名进 `extra_rules.json` |
| 某要点明明是外部评价却报缺项 | 加入 `EXTERNAL_PAT` | 脚本 `EXTERNAL_PAT` |
| 某要点要的是"无相关情形"证明 | 加入 `REVERSE_PAT`，会在清单里标注「反向证明类」 | 脚本 `REVERSE_PAT` |
| 指标用词与文件名对不上 | 补 `SYNONYM` 词对 | 脚本 `SYNONYM`（通用词对才进包） |
| 年度窗口不对 | 参评年度变化后窗口要跟着调 | `--window 2024,2026` |

机构名、项目名、合作方名属**公开信息**，可安全写进规则；**不得写入捐赠人、受益人、员工个人信息**。

## 六、v1 → v2 的教训（为什么改成现在这样）

| v1 做法 | 后果 | v2 改法 |
|---|---|---|
| 特征词含二级指标名 | 通名（"财务"）让 0.3 分的"会计人员配备"命中 265 个文件 | 特征词只取三级名 + 考查要点 |
| 无门控，规则命中即指派 | 规则覆盖 `3.2` 全部要点 → 整个业务库同时命中十几项，某要点 1154 个候选 | 加词面门控（≥2，或 ≥1 且规则 ≥3） |
| 暴力比对 | N 项 × M 文件次子串检索 | 倒排索引（词 → 文件 id），0.3 秒建索引 |
| 置信度只看"是否有规则命中" | 候选全部来自规则，于是 `待确认` 恒为 0，置信度失效 | high 只给该文件的最优归属要点，且要求词面分 ≥4 |
| 过宽要点照常放入 Top N | 相当于随机挑文件进归档树，制造"已齐"假象 | 过宽要点不实体化，只登记待人工挑选 |
| 反向证明类/外部征询类视为缺项 | 把"本就不需要材料"的项报成缺口，误导补料方向 | 新增 `外部征询` 状态与「反向证明类」标注 |

**通用教训**：自动化匹配的价值不在"覆盖率高"，而在**把不确定明确标出来**。把不确定标成已归位，比标成缺项危险得多。

## 七、人工复核纪律

`待人工确认清单.csv` 是**必须由机构人员逐行判定**的队列（含"命中来源"列，让人一眼看出机器凭什么这么配）：

- 对口 → 该行改判「已归位」，从缺项里划掉对应要点；
- 部分对口 → 保留已对口文件，其余仍为缺项；
- 不对口 → 该文件移出目标文件夹，要点退回缺项重找。

**判定结果要回写**（`match_report.json` 或机构自建台账），否则每次重跑都要重判一遍。
