# 存量材料盘点与归位

把「已经堆在磁盘上的机构资料」，变成「按指标排好的归档树 + 一张缺项清单」。

**它解决的是迎评准备里最耗时、最容易失控的一段**：机构不是没有材料，是材料散在几十个目录里、和评估指标对不上号。上游指标拆解环节产出的是**空文件夹树**，等负责人放料；本技能反过来——**先把盘上已有的自动就位，再输出差什么**，负责人打开文件夹时大部分材料已在位。

## 一、适用场景与前置条件

**适用**：机构自有资料库整理归位；跨机构服务时对客户存量做摸底；多年积累的媒体素材（照片/视频/底片）筛选代表件。

**前置条件**：

| 前置 | 说明 | 缺失时的处理 |
|---|---|---|
| 归档文件夹树 | 已由上游指标拆解环节生成（编号与主表一致） | 先跑上游环节；本技能不自行发明文件夹结构 |
| `enriched_meta.json` | 全量末级要点元数据（含 `folder` 字段；**项数随指标版本而定，不预设固定值**） | 由上游指标拆解环节产出，格式见 §八 |
| 扫描根目录清单 | 用户**显式指定**的目录（可多个） | 缺则先问，**不得自行推断或扫盘符根** |
| 机构专名规则（可选） | `<工作目录>/extra_rules.json`：项目名/部门名/属地党建专名 | 缺则按通用规则匹配，3.2 类业务板块命中率会偏低；格式见 `references/match-rules.md` §五 |
| 就位模式 | `index` / `link` / `copy` | 默认 `index`；选 `copy` 必须先看体积预演 |

## 二、六步流水线

```bash
S="<本技能目录>/scripts"

# 1) 只读扫描 → inventory.json（根目录由用户显式指定，可多个；标签=路径）
python "$S/scan_inventory.py" \
  --root "行政与治理=<机构制度、证照、理事会档案所在目录>" \
  --root "业务项目=<项目档案所在目录>" \
  --root "政务=<民政、党建往来文件所在目录>" \
  --root "公开宣传=<官网、公众号、媒体报道所在目录>" \
  --out "<工作目录>"

# 2) 匹配指标 → match_report.json
python "$S/match_items.py" --work "<工作目录>"

# 2.2) 主体区分（资料可能混杂时必做；只标注不移动任何文件）
python "$S/classify_entity.py" --work "<工作目录>" --rules "<工作目录>/entity_rules.json" \
  --inplace --filter-match-report
#   → inventory.json 增加 entity 字段；产出 affiliate_index.json / entity_summary.json
#   → 主体候选单独落 match_report_self.json，后续步骤一律用它

# 3) 归位（默认预演→出清单；确认体积后加 --execute 才动文件）
#    已做主体区分时，务必用 --match 指向主体报告，否则关联方材料会一起被归位
python "$S/place_files.py" --work "<工作目录>" --archive "<归档根>" --mode copy \
  --match "<工作目录>/match_report_self.json"

# 4) 一致性校验（退出码 0 才交付）
python "$S/validate_placement.py" --work "<工作目录>" --archive "<归档根>"

# 5) 同名多版本检测（现场出示错版本是现实失分点）
python "$S/report_duplicates.py" --work "<工作目录>" --only-placed

# 6) 归位结果回填清单主表（默认只出 CSV；加 --insert 才写入 xlsx，写入前自动备份）
python "$S/backfill_to_checklist.py" --work "<工作目录>" --archive "<归档根>" \
  --xlsx "<自评资料准备清单（分发版）.xlsx>" --insert
```

产出：

```
<工作目录>/
  inventory.json          # 存量索引（路径/类型/大小/年度推断）
  match_report.json       # 末级要点 × 命中文件 × 置信度 × 状态
  placement_plan.json     # 就位计划（实体化 / 仅登记）
  归位体积预演.md          # 体积与原因分布（给人看）
  缺项清单.csv             # 需要补什么
  待人工确认清单.csv       # 机器没把握的，交人判
  同名多版本清单.csv       # 同一文档的多个版本（防现场出示错版本）
  主表_存量材料列.csv      # 第6步：回填主表的三列对照数据（可单独交付）
```

第 6 步产出的三列（写入主表，位于【电子版自评资料清单】右侧）：
**当前文件夹内已有资料（存量已放入）** / **存量归位状态** / **尚缺/待处理提示**。


## 三、核心概念

| 概念 | 定义 |
|---|---|
| **载体分层** | `doc`（文档/表格/PDF）、`image`（照片截图）、`video`、`raw`（CR2 等底片）、`other` |
| **实体化** | 真正进归档文件夹（复制或硬链接）；`raw` 与超限媒体一律**不实体化**，只登记指针 |
| **多指派** | 一个文件可同时支撑多个要点（如审计报告既撑财务也撑公益支出），得分达最优值 80% 的候选都被指派 |
| **置信度** | `high`＝强规则命中且目标前缀覆盖该要点二级指标且年度在窗口内；`medium`＝仅词面重合或权重不足 |
| **状态四档** | `已归位`（有 high）/ `待确认`（只有 medium）/ `外部征询`（材料由评估方或第三方出具）/ `缺项`（无命中）。四档之和 = 要点总数，见 `references/gap-report-spec.md` |
| **痕迹类要点** | 要点文本含纪要/记录/签到/照片/台账/成效等词——**光有制度不算，必须有执行留痕**，是缺项重灾区 |
| **年度窗口** | 参评年度前推三年（默认 2023–2025，用 `--window` 按参评年度调整），仅影响排序与置信度，不决定是否指派 |

## 四、关键规则

### 1. 载体政策（防止 37G 媒体灌爆归档树）

| 载体 | 默认政策 | 理由 |
|---|---|---|
| `raw`（CR2/ARW/NEF） | **永不实体化** | 单文件 20–60MB，且本质是原片，评估只需代表图 |
| `video` | 单文件 ≤ 60MB 且每项 ≤ 1 个 | 视频无检索价值，评估现场看图不看片 |
| `image` | 单文件 ≤ 8MB 且每项 ≤ 4 张 | 痕迹类证据只需代表件；排序取年度内、高分候选 |
| `doc` | 每项 ≤ 25 个，>150MB 仅登记 | 文档才是审查主体，保留完整 |

参数可用 `--max-*-per-item` / `--max-*-mb` 调整。**任何情况下 `raw` 都不实体化**。

### 2. 三种就位模式

见 `references/placement-modes.md`。要点：`index` 零占用、可反悔；`link` 同盘零占用但跨盘失败、上传共享盘会变真复制；`copy` 才能真正打包分发，但体积翻倍。

### 3. 过宽要点不实体化（重要）

机构的**项目材料按"项目"组织，指标按"管理环节"组织**（论证/申报 → 运作 → 结项），同一项目文件夹里申报书、执行协议、结项总结混在一起，文件名不含环节语义——**这是结构性矩阵，任何关键词规则都无法自动切分**。脚本会检出这类要点（候选 > 60），并一律不实体化、只登记候选，转为人工挑选工单。**不要靠继续加关键词去"修复"它**，详见 `references/match-rules.md` §四。

### 4. 预演强制

`place_files.py` **默认 dry-run**：写出就位计划、体积预演、缺项清单与待确认清单，但不动任何文件。选 `copy` 时必须先把体积报给用户确认，得到确认后才追加 `--execute`。这不是流程礼节，是防止无告知地占用几十 GB。

> 清单在预演阶段就已产出——因为清单是交付物，不该以"执行文件操作"为前置。

### 5. 同名多版本检测（易被忽略的失分点）

机构存量里同一份文档常有多个版本（制度原件版／官网截图版／扫描件版），**文件名相同、内容与大小不同**。评估现场若出示了旧版本或缺附件页的版本，会直接影响"制度是否落实""材料是否规范"的判断。`report_duplicates.py --only-placed` 会列出这些文件族与涉及指标编号，归档前须确定唯一权威版本。

### 6. 归位结果必须回填清单（否则归档树是黑箱）

归位完成后，负责人打开主表看到的仍是"要准备什么"，看不到"已经放了什么"——
结果是把已就位的材料重做一遍。第 6 步把三列写进主表
（已有资料清单 / 归位状态 / 尚缺提示），让"要求"与"现状"在同一行对齐。

两条铁律：**①以磁盘实际为准**（不用计划清单），并逐项交叉核验；
**②不得让"待确认"看起来像"已完成"**——见 `references/backfill-spec.md`。


### 7. 主体区分（资料混杂时必做）

用户资料常把参评机构与合作/关联机构混在一起。**不区分就会把别人的材料算成本机构的得分依据**——这是最隐蔽的偏差。

- 先建 `entity_rules.json`（规范见 `references/entity-rules-spec.md`），回读给用户确认主体别名与关联方名单；
- 跑 `classify_entity.py` 标出 `SELF / JOINT / AFFILIATE / UNKNOWN`；
- **后续一切"已归位"判定只认 `match_report_self.json`**；某要点剔除非主体候选后为空 → 改判 `缺项` 并在缺项清单注明"原候选为关联方材料"；
- `AFFILIATE / JOINT` 归入 `90-关联方资料-仅供风险核查/`，与主体归档树物理隔离，产出 `affiliate_index.json`；
- `UNKNOWN` 进 `待指派归属清单.csv`，交用户指派后再定。
- 规则与用途边界见 `references/entity-separation.md`。**关联方资料不得计入主体评分，不得顶替主体自证。**

## 五、安全边界（硬规则，不可协商）

见 `references/safety-boundary.md`。摘要：

1. **只扫用户显式指定的目录**，绝不自动扩展到盘符根（`E:\`、`C:\`）或用户主目录；
2. **全程只读源**：不移动、不重命名、不删除任何源文件；归位只做「新增副本」或「新增链接」；
3. **个人目录特殊对待**：桌面/下载/文档/微信文件目录视为只读，除非用户明确点名且目的合理；
4. **归档根不得位于扫描源目录内部**（脚本会拒绝，防递归复制）；
5. **不覆盖原件**：目标文件夹内同名文件自动加 `_01` 后缀，绝不覆盖已有文件；
6. **可反悔**：`index` 模式零副作用；`copy` 模式的归档树可整体删除重建，源目录不受影响。

## 六、交付前自检

- [ ] `inventory.json` 的文件数与 `find <root> -type f` 计数一致（排除系统目录后）
- [ ] **四档之和 = 要点总数**（已归位 + 待确认 + 外部征询 + 缺项）
- [ ] `copy` 模式已报告体积并获用户确认
- [ ] `缺项清单.csv` 行数 = 缺项数；`待人工确认清单.csv` 行数 = 待确认数
- [ ] 过宽要点（候选 > 60）已在对话中单独列出，并说明需人工挑选
- [ ] 反向证明类、外部征询类已在清单"类别标注"列写明
- [ ] 每个有材料的文件夹内都有 `取材指针.md`（含未实体化文件的原始路径）
- [ ] `validate_placement.py` 退出码 0
- [ ] 已跑 `report_duplicates.py --only-placed`，同名多版本文件族的权威版本已确认
- [ ] 缺项中的**痕迹类高分项**已在对话中单独点出（这是机构最需要补的）
- [ ] **汇报时把"待确认"与"已归位"分开**，不合并成完成度百分比
- [ ] 第6步回填后：表内条目逐项等于归档目录实际文件数（0 不一致）
- [ ] 第6步回填后：数据验证与自动筛选已迁移到新列位置，「使用说明」已补三列含义
- [ ] 写入 xlsx 前已备份，并把备份路径告知用户

## 七、常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 覆盖率异常高但全是 `待确认` | 强规则没命中，只靠词面重合 | 在 `<工作目录>/extra_rules.json` 补机构专用关键词（项目名、部门名），重跑；机制见 `references/match-rules.md` §五 |
| 某业务板块文件全挤进少数要点 | 业务领域规则过宽 | 在 `extra_rules.json` 中为该板块加更具体的专有名词（机构项目名） |
| 年度排序不对（新旧材料不分） | 年度窗口与参评年度不匹配 | `--window <起始年>,<结束年>`（参评年度前推三年） |
| 归档树体积远超预期 | 媒体未封顶或 doc 上限太高 | 调 `--max-image-per-item` / `--max-video-mb`；检查是否有大 PDF 扫描件 |
| 复制中断产生 0 字节文件 | 磁盘满或路径过长 | `validate_placement.py` 会报出；删掉 0 字节文件后重跑 |
| 校验报"大小不符"但内容看起来没错 | **同名不同源**的文件在就位时按设计加了 `_01` 后缀，而校验若只按原文件名比对就会误判 | 校验须在"同名族"里按大小命中（脚本已修）；同名族本身是风险，跑 `report_duplicates.py` |
| 同一份文档在归档树里出现两份且大小不同 | 存量里"制度原件版"与"官网截图版"常同名 | `report_duplicates.py --only-placed` 出清单，归档前确定唯一权威版本 |
| 回填后列宽错位、筛选失灵、下拉框跑位 | 插列属结构操作，列宽/数据验证/筛选**都不会自动跟随** | 见 `references/backfill-spec.md` §三，脚本已处理；改表后务必逐项自检 |
| 本地编辑器通道批量调用中途断连，改动全丢 | editor_sdk 服务可能停止且内存改动未落盘 | 每完成一个阶段就 `save_file`；批量结构操作**首选直接写盘**并先备份 |
| 回填内容与计划清单不一致 | 用了 `materialize` 计划而非磁盘终态 | 一律以磁盘扫描为准，两者互校 |
| 中文路径报错 | 多层 shell 转义 | 用脚本传参，避免内联命令里嵌中文路径 |
| Windows 长路径超 260 字符 | 指标短名 + 文件名叠加 | 归档树已用两位编号压短；必要时在目标文件夹内再缩短文件名 |

## 八、上下游衔接

本技能的输入是「归档文件夹树 + 逐项要点元数据」，这两样可来自指标拆解类工具，也可手工准备。

**前置输入（任选其一）**：

| 输入 | 来源 | 缺失时的替代做法 |
|---|---|---|
| 归档文件夹树 | 由指标拆解环节生成（编号与主表一致） | 按官方指标表的一/二/三级编号手工建树，编号规则见 §四.2 |
| `enriched_meta.json`（全量末级要点元数据，含 `folder` 字段） | 由指标拆解环节产出 | 按指标表逐项整理成同样的 JSON（字段：`code` / `text` / `score` / `type` / `folder`） |

**下游产出**：归位结果可直接用于打分预演（哪些要点有材料、哪些缺）与补料台账（缺项转化为
「问题 / 整改动作 / 责任角色 / 时限 / 证据形式 / 复查时点」六字段）。

**交付物语序**：第 6 步回填后的主表，是分发到负责人的那一份——「清单要求 + 文件夹现状 + 尚缺提示」同行对照，
负责人照此行准备即可；归档树是物证现场，主表是指挥图。
